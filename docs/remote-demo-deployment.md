# Remote demo deployment and acceptance

This is preparation only. Do not publish an endpoint until the owner authorizes the specific endpoint after the preflight below. Remote-device acceptance is **not yet passed**. Use only synthetic media, a separate demo company, accounts, devices, application key, storage and an empty demo database. Never point these instructions at the primary CMS database or the broken acceptance database account.

## Option 1: Tailscale Funnel (recommended for a short test)

Funnel makes the endpoint public, not private to the tailnet. It requires an eligible Tailscale account, MagicDNS, HTTPS and Funnel enabled in tailnet policy; it uses a `*.ts.net` hostname and has non-configurable bandwidth limits. Confirm current requirements and commands in [Tailscale Funnel documentation](https://tailscale.com/docs/features/tailscale-funnel) and [CLI reference](https://tailscale.com/docs/reference/tailscale-cli/funnel). Obtain the intended node hostname before setting APP_URL. Account or policy changes and publication require the responsible owner's action.

1. Prepare a separate checkout and environment outside the real installation. Create an empty demo-only MySQL database and a unique database user restricted to that database, with only the privileges required by migrations and application operations. Keep MySQL bound to loopback; never expose port 3306. Do not copy production data, `.env`, storage, credentials or player journals. Use strong unique demo credentials, a new `APP_KEY`, and least-privilege CMS users. Verify the target database and user before migrations; never run acceptance fixtures against any real database.
2. Install the repository's PHP and Node dependencies, run `npm ci` and `npm run build`, then run migrations against the verified empty demo database. Provision only necessary demo users, permissions and a demo company. Review registration and account approval for the intended test: avoid leaving an unintended public registration path open; apply access controls at the edge or disable registration for the demo if necessary. Confirm password-reset mail and administrative privileges are appropriately configured.
3. In the separate demo `.env`, set `APP_ENV=production`, `APP_DEBUG=false`, a new `APP_KEY`, `APP_URL=https://<exact-node-name>.ts.net`, `SESSION_SECURE_COOKIE=true`, `SESSION_HTTP_ONLY=true`, `SESSION_SAME_SITE=lax`, and a host-only session cookie (leave `SESSION_DOMAIN` unset). Set `DEMO_TRUST_HOST=true` and `DEMO_TRUST_PROXY=127.0.0.1,::1` only when the local app is reachable exclusively through the local proxy. The trusted host matches the exact APP_URL host. Trust only the actual proxy addresses, never `*`; check which address Funnel uses locally. Clear/rebuild configuration cache after changes. Do not set `PLAYER_WINDOWS_DOWNLOAD_URL` until the release workflow below is complete.
4. Serve the Laravel **public** directory only, bound to loopback. For a short demo Laravel's local server may be run as `php artisan serve --host=127.0.0.1 --port=8000`; never expose this port directly. This single-process server is suitable only for limited testing: uploads and large media transfers can block other requests. Confirm PHP upload limits (`upload_max_filesize`, `post_max_size`), web server limits and timeouts cover the selected small test files. Never serve the repository root, `.env`, private storage, or phpMyAdmin.
5. Before publication, perform the security preflight below and obtain explicit authorization. After authorization only, start Funnel using the current documented CLI, e.g. `tailscale funnel 8000`. Confirm the exact HTTPS origin and valid certificate, then verify the local app sees the intended HTTPS scheme and host. Laravel's [trusted proxy and host documentation](https://laravel.com/docs/13.x/requests#configuring-trusted-proxies) explains forwarded headers and host validation. Verify redirects, generated media URLs, CSRF and secure cookies through the public origin; do not weaken TLS validation in Player. If proxy source/header behavior is unclear or host/scheme checks fail, stop and fix the topology before testing.

### Security preflight (before public exposure)

- Confirm isolated database, user, storage, APP_KEY, synthetic data and test devices; confirm no primary credentials/data are in the demo. Confirm backups and a named operator for shutdown.
- Confirm debug off, production assets built, exact host validation, loopback-only upstream, trusted proxy limited to actual local address, and HTTPS/secure cookies. Test a forged Host and forwarded headers directly against the local upstream and through the proxy: unknown hosts must be rejected and untrusted sources must not control scheme/host. Ensure no direct network route reaches the app or database.
- Check authentication, account status, company isolation and device token authorization; use unique strong test passwords and short-lived activation codes. Restrict or disable registration as needed. Assess rate limits: a reverse proxy can collapse client IPs or supply spoofable forwarded addresses, so verify effective client IP and throttling before exposure. Review logs without recording credentials.
- From outside, after authorization, check that `.env`, source files, private storage, directory listings, debug pages, phpMyAdmin and MySQL are inaccessible. Check TLS certificate, redirects and session cookies. If any fail, shut down Funnel immediately.
- Keep the test window short and monitor disk, upload size, network usage and logs. Do not expose ports for Vite, database, or administration tools. Public media must only be accessed through authorized device endpoints.

## Option 2: Oracle Cloud Always Free VM

For a longer independent test, use a separate Always Free eligible VM and isolated demo database, subject to current region capacity, account eligibility, quotas and terms. Oracle can reclaim idle instances; see [Always Free resources](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm). This requires an Oracle account, VM provisioning, a hostname and valid TLS certificate, and explicit authorization before any public endpoint or DNS change. Use a maintained OS and web server serving only Laravel's `public` directory, a local private MySQL service, backups, updates and least-privilege accounts. Allow inbound HTTPS and only restricted administrative access; deny public MySQL, HTTP application ports and phpMyAdmin. Configure exact trusted host and only the actual reverse proxy address, secure sessions, PHP request limits and APP_URL as above. Repeat the complete preflight and acceptance; cloud hosting is not automatically production-ready. Costs and free-tier limits must be checked in the account before provisioning.

## Windows installer release workflow (manual)

No published release asset is assumed. Build or locate the intended 2.0.0 x64 installer in a controlled environment; verify its provenance and run `Get-FileHash -Algorithm SHA256 <installer>` on Windows. The digest must equal `5A9A5F8947200828E72841F747FD25616B5163A34CB7FECFFC2E1756F041A45D`. If it differs, stop: do not publish or use the displayed checksum until the artifact and release metadata are reconciled. The build may be unsigned; disclose signing status and validate it independently. After separate owner authorization, create the appropriate GitHub Release manually, upload only the verified installer, download the published asset and verify its digest again. Set `PLAYER_WINDOWS_DOWNLOAD_URL` to that exact HTTPS asset URL, clear/rebuild Laravel configuration cache, and verify the landing link and downloaded hash. URL syntax validation alone does not verify the file or availability; the operator is responsible for verification. Never publish credentials, `.env`, journals, caches or private media.

## Remote-device acceptance checklist

Record date, tester, public origin, CMS commit, Player version, test network/device, result and evidence for each step. Use a device on a genuinely different network (for example, mobile hotspot), not merely a second browser on the host. Avoid recording tokens or activation codes in evidence.

- [ ] Open landing page externally over HTTPS; check redirects and exact host. Verify mobile and desktop layout.
- [ ] Log in on a separate device; check secure cookie, CSRF and the permitted landing route.
- [ ] If a verified release is configured, download via landing page and compare SHA-256; otherwise record unavailable.
- [ ] Install on Windows 10/11 x64. Enter the HTTPS origin and activate using a newly generated demo device code.
- [ ] Assign a playlist without a schedule; verify manifest and assignment apply.
- [ ] Download synthetic video and image. Verify authenticated private media access and denial without credentials or across company/device scope. Capture status and headers without secrets: a valid `Range: bytes=0-99` yields 206, `Content-Range: bytes 0-99/<size>` and 100 bytes; an unsatisfiable range yields 416 and `Content-Range: bytes */<size>`. Check proxy does not strip Range or alter content.
- [ ] Play two windows simultaneously; temporarily disconnect the device after media is cached, verify offline playback, then reconnect.
- [ ] Confirm heartbeat and Proof of Play events arrive after reconnect; inspect request sizes, rate limits, timeouts, bandwidth and reverse-proxy headers. Do not log bearer tokens.
- [ ] Export Proof of Play to XLSX using an authorized account and check its contents. Record any failures and retest after correction.

## Shutdown / rollback

Disable Funnel using the current CLI (`tailscale funnel off` for the relevant listener; confirm with `tailscale funnel status`), stop the local server and verify externally that the endpoint no longer responds. Revoke demo device credentials and accounts, remove access to the demo database, and securely dispose of demo data according to the owner's retention decision. Revert demo-only environment settings and remove configured release URL if needed; clear configuration cache. For a VM, close ingress and stop or terminate only the explicitly identified demo resources. Never delete the primary database or user data.
